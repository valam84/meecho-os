# Ускоритель CB2: эталон и как его снимать

Mali-G52 (Bifrost) платы BIGTREETECH CB2, узел `gpu@fde60000`. Всё здесь
снимается с вендорского Linux на плате (6.1.115-btt-rockchip64) **до**
того, как служба `minix/drivers/video/mali/` трогает железо.

| Файл | Что |
|---|---|
| `capture.sh` | снимок: какой драйвер владеет узлом (kbase или panfrost), его отчёт, узел дерева, такты, домен питания, `vdd_gpu`, прерывания; CRU, PMU и регистры ускорителя через `/dev/mem` |
| `ref-idle.txt` | снимок 2026-10-13 как есть: panfrost в простое, домен выключен — регистры ускорителя скрипт не читал |
| `ref-on.txt` | снимок 2026-10-13 с `power/control = on`: домен включён, panfrost на 200 МГц, все регистры ускорителя — **эталон** |
| `jobprobe.py` | зонд заданий через ioctl panfrost, без пакетов: одно WRITE_VALUE и цепочка из 64 (заливка буфера), проверка процессором; рядом регистры MMU и слотов |
| `ref-jobs.txt` | его вывод 2026-10-13: **все задания исполнились** — эталон второй половины 11.5 |
| `ref-fault.txt` | `jobprobe.py fault` 2026-10-13: задание на неотображённый адрес — отказ MMU, что сделал panfrost, цепочка после — эталон линии MMU (73) |
| `meecho-first-run.txt` | журнал службы `mali` на MEECHO (2026-10-13, `kmsg`): `probe=1`, запуск, остановка, повторный запуск, `refresh` |
| `meecho-jobs.txt` | журнал службы с цепочкой заданий (тот же день): своя MMU, 64 WRITE_VALUE, 0 неверных слов — три запуска |
| `meecho-fault.txt` | журнал службы с `faulttest=1` (тот же день, `kmsg -f`): отказ по линии 73 с адресом `0x2010040`, `FAULTSTATUS` и слот как в `ref-fault.txt`, цепочка после отказа чистая — пять прогонов |
| `ref-api.txt` | `jobprobe.py api` (2026-10-14, веха 11.6): что panfrost отвечает на каждый вызов интерфейса, который служба отдаёт клиентам, — версия, возможности, 45 параметров, места буферов по порядку, ошибки, ожидания со сроками, объекты синхронизации, отказ задания, куча — **эталон интерфейса** |
| `ref-two.txt` | `jobprobe.py two`: два клиента разом, у одного на 50-м круге отказ — что видит каждый, в каких окнах их задания |
| `meecho-api.txt`, `meecho-two.txt` | то же от программы MEECHO (`port/test/mali/pftest.c`) через службу: строка в строку против `ref-*.txt`, 5 расхождений из 96 — все объяснены в PORTING-LOG («Этап 11.6, первая часть») |
| `meecho-iface.txt` | журнал службы того прогона (`kmsg`), 500 цепочек по 0,16 мс, самопроверка 11.5 с отказом через код 11.6 |
| `ref-heap.txt` | `jobprobe.py heap` (2026-10-14): куча 64 МиБ растёт по отказам — первый кусок, тот же, последний, одно задание через 16 новых, за концом кучи; регистры во время первого роста, `dmesg` — **эталон роста кучи** |
| `meecho-heap.txt` | `pftest heap` на MEECHO и журнал службы (`log=3`): 19 ростов, из чего складываются 5,5 мс куска |
| `ref-cost.txt`, `meecho-cost.txt` | `jobprobe.py cost` и `pftest cost`: та же цепочка с большим буфером в списке задания, не отображённым и отображённым процессором, — цена обслуживания кэша службой (у panfrost без `WB_MMAP` она ноль) |

Снимать (плата под Armbian, по ssh, под root):

    sh capture.sh    > idle.txt    как есть
    sh capture.sh on > on.txt      драйвер держит блок включённым
                                   (power_policy always_on у kbase или
                                   power/control on у panfrost), потом
                                   прежнее значение возвращается

Регистры ускорителя скрипт читает, только если PMU говорит, что домен
PD_GPU включён и не в простое, а CRU — что вентили `clk_gpu_src` и
`clk_gpu` открыты и сбросы отпущены: чтение обесточенного или
незатактированного блока на Rockchip вешает шину.

## Что ответила плата (2026-10-13)

**Драйвер — `panfrost`** (модулем; `CONFIG_MALI_BIFROST is not set`, kbase в
этом ядре нет). `dmesg`: `mali-g52 id 0x7402 major 0x1 minor 0x0 status
0x0`, `shader_present=0x1 l2_present=0x1`. Прерывания: GIC 71
`panfrost-gpu`, 73 `panfrost-mmu`, 72 `panfrost-job`.

Регистры ускорителя при включённом блоке (`ref-on.txt`):

| Регистр | Значение | Что значит |
|---|---|---|
| `GPU_ID` | `0x74021000` | Mali-G52 (0x7402), r1p0 |
| `L2/CORE/TILER/MEM_FEATURES` | `0x07110206`/`0x2`/`0x209`/`0x1` | |
| `MMU_FEATURES` | `0x2823` | 35 бит VA, 40 бит PA |
| `AS_PRESENT` / `JS_PRESENT` | `0xff` / `0x7` | 8 адресных пространств, 3 слота заданий |
| `SHADER/TILER/L2/STACK_PRESENT` | `1`/`1`/`1`/`1` | **одно** шейдерное ядро (два исполнительных блока) |
| `THREAD_MAX_THREADS` | `0x300` | 768 |
| `COHERENCY_FEATURES` | `0` | кэши процессора ускоритель не видит — обслуживать их явно |
| `JM_CONFIG` | `0x000f0000` | запись panfrost: размер группы IDVS (особенность G52) |
| `SHADER/TILER/L2_MMU_CONFIG` | `0` | |

Обвязка:

| Регистр | В простое (600 МГц) | За работой (200 МГц) |
|---|---|---|
| PMU `PWR_STATUS` | `0x7f` — PD_GPU выключен | `0x7e` — включён |
| PMU `IDLE_ACK`/`IDLE_ST` | `0x1ee` — шина в простое | `0x1ec` |
| CRU `CLKSEL_CON6` | `0x4951`: gpll/2 = 594, **ядро на PVTPLL** | `0x4155`: **gpll/6 = 198, путь PLL**, aclk /2, pclk /5 |
| CRU `CLKGATE_CON2` | `0x1c0` | `0x1c0` — `clk_gpu_src` и `clk_gpu` открыты |
| CRU `SOFTRST_CON2` | `0` | `0` |
| `vdd_gpu` | 900 мВ, включён | то же |

`CLKSEL_CON6` ставит прошивка по запросу SCMI: на 200 МГц она сама уводит
ядро на путь PLL, PVTPLL — только на высоких частотах. **`clk_summary`
Linux показывает cpll/500 МГц** — это значение загрузчика (MEECHO после
загрузки находит `0x4191`, cpll/2 = 500 МГц): мультиплексоры для Linux
только для чтения, он прочёл их один раз при старте. Верен только регистр.

Отсюда служба: такт она ставит в слово `0x4155` (делитель считается от
gpll, сравнивается с эталоном) — самая медленная точка таблицы, 0.85 В, а
`vdd_gpu` грузится с 0.9; после подъёма ядер печатает свои регистры
рядом с эталоном, помечая расхождения `DIFFERS`.

## Задания на этом железе (`ref-jobs.txt`)

Раскладка дескриптора — из Mesa (`src/panfrost/genxml/v7.xml`, MIT):
заголовок 32 байта (слово 4: бит 0 `is_64b`, 7:1 тип, 31:16 индекс; слова
6–7 — следующее задание), нагрузка WRITE_VALUE с байта 32 — адрес, тип
значения (6 — 32 бита), значение с байта 48. Panfrost кладёт буфер на VA
`0x2000000`.

| Что | Итог |
|---|---|
| одно WRITE_VALUE | 0.35 мс; в буфере `0xc0ffee42`, соседнее слово не тронуто; состояние в заголовке `0x1` |
| цепочка из 64 (каждое пишет своё слово) | 0.24 мс; 0 неверных слов; состояние первого и последнего `0x1` |
| `AS0 TRANSTAB` | `0x7bdc6007`: корень таблиц + `ADRMODE_TABLE` (3) + `READ_INNER` (бит 2); `SHARE_OUTER` нет — ускоритель не когерентен |
| `AS0 MEMATTR` | `0x888d88`: атрибуты 0 и 2 — `0x88` («по умолчанию реализации»), 1 — `0x8d` (с выделением при записи) |
| `AS0 TRANSCFG` | `0` — старый режим LPAE (panfrost этой версии пишет только `TRANSTAB` и `MEMATTR`) |
| `JS1 CONFIG` | `0x7b00`: очистка кэшей до (`3<<8`) и после (`3<<12`), флаг цепочки (бит 11, panfrost его чередует — у следующего `0x7300`), сокращение очисток (бит 14), AS 0; `AFFINITY` 1 |
| `JM_CONFIG` | `0x000f0000` и до заданий |

Корень таблиц через `/dev/mem` не читается (`STRICT_DEVMEM`): формат
записей — из `io-pgtable-arm.c` (`ARM_MALI_LPAE`), проверять своим
заданием.

## Отказ MMU на этом железе (`ref-fault.txt`)

`python3 jobprobe.py fault` (2026-10-13): цепочка, одно WRITE_VALUE на
`va + 0x10040` — запись 16 таблицы последнего уровня, где буфер 16 КиБ
занимает записи 0–3, — и цепочка снова. Пока panfrost разбирается,
зонд опрашивает регистры (раз в ~19 мкс: Python) и печатает каждое
изменение; всё уложилось между двумя опросами, видно конечное состояние
через 184 мкс после `SUBMIT`.

| Что | Итог |
|---|---|
| `MMU_IRQ_RAWSTAT` | `0x1` — отказ страницы AS0, не ошибка шины |
| `AS0 FAULTSTATUS` | `0x7c1003c3`: исключение `0xC3` `TRANSLATION_FAULT_3` (уровень с нуля, пустая запись последнего уровня), доступ 3 — запись, «slave», источник `0x7c10` |
| `AS0 FAULTADDRESS` | `0x2010040` — **ровно записанный адрес**, не страница |
| что сделал panfrost | `Unhandled Page fault in AS0`; адресное пространство выключено: `TRANSTAB 0`, `MEMATTR 0`; маска `MMU_IRQ_MASK` `0xfe00fe` — AS0 замаскирован |
| задание | упало: `JS1 STATUS 0x48` — **`JOB_BUS_FAULT`**, не код MMU; `js fault, js=1, status=JOB_BUS_FAULT`; заголовок задания `0` — записать его было уже некуда |
| после выключения | **`MMU_IRQ_RAWSTAT` снова `0x1`** под маской, хотя `panfrost_mmu.c` пишет `MMU_INT_CLEAR` до выключения; `GPU_STATUS 0x10` |
| следующее задание | AS0 снова с теми же таблицами (по исходнику — бит сброшен, маска снята, потом `enable`): цепочка из 64 — 0 неверных слов, `RAWSTAT 0`, `GPU_STATUS 0` |

Отсюда служба: выключить адресное пространство — значит уронить
задание; ждать обе половины (линию MMU и отказ задания), в любом
порядке; **перед снятием маски бит сбросить**, иначе старый отказ
придёт как новый.

Служба MEECHO (`meecho-fault.txt`) делает в том же порядке и читает
`RAWSTAT` между шагами: после сброса `0`, после выключения `1` — бит
поднимает само выключение (ждавший доступ отказывает ещё раз), а
задание к этому моменту уже упало (`0x48`). Остальное — регистр в
регистр с таблицей выше.

## Из дерева

| Что | Значение |
|---|---|
| `compatible` | `arm,mali-bifrost` (только он; mainline пишет перед ним `rockchip,rk3568-mali`) |
| `reg` | `0xfde60000`, 16 КиБ |
| прерывания | SPI 39 `gpu`, SPI 41 `mmu`, SPI 40 `job`, и те же три ещё раз заглавными — для kbase |
| такты | `<scmi_clk 1>` «gpu» — такт прошивки (SCMI через `smc`); `<cru 27>` «bus» — `CLK_GPU`, вентиль `CLKGATE_CON(2)` бит 3 |
| домен | `<power 7>` — `RK3568_PD_GPU`: бит 0 в `PWR_CON`/`PWR_STATUS`, бит 1 в `IDLE_REQ`/`IDLE_ACK`/`IDLE_ST` |
| питание | `mali-supply` → `vdd_gpu` = `DCDC_REG2` PMIC, `always-on`, `boot-on` — **драйвер PMIC для 11.5 не нужен** |
| частоты | `opp-table-1`: 200/300/400 МГц при 0.85 В, 600 — 0.9, 700 — 0.95, 800 — 1.0 (выше загрузочной — веха 11.8) |

Справка о регистрах — `panfrost_regs.h` и regmap kbase вендорского ядра
(`armbian/linux-rockchip`, ветка `rk-6.1-rkr5.1`), `pm_domains.c`,
`clk-rk3568.c`; под GPL, в дерево не кладутся — берутся номера и порядок
действий.

## Служба на MEECHO (2026-10-13, `meecho-first-run.txt`)

Что оставляет загрузчик: `CLKSEL_CON6` `0x4191` (cpll/2 = 500 МГц, путь
PLL), вентили `0`, сбросы отпущены, **PD_GPU выключен, шина в простое**;
gpll — 1200 МГц (под Linux 1188). Служба с первого запуска: такт в
`0x4155` (gpll/6 = 200 МГц), домен включён, `GPU_ID 0x74021000`, сброс,
ядра готовы, **0 регистров расходятся с эталоном**, линия 71 доказана
прерыванием. Остановка гасит ядра; повторный запуск находит такт и домен
включёнными и ничего не переписывает; `refresh` — то же.

## Интерфейс Panfrost: panfrost и MEECHO (2026-10-14, веха 11.6)

Снимать (плата под Armbian, root): `python3 jobprobe.py api >
ref-api.txt`, `python3 jobprobe.py two > ref-two.txt`. На MEECHO то же —
`pftest api`, `pftest two` (служба `mali` запущена с `-dev
/dev/dri/renderD128`). Сравнивать: `diff <(sed '/^dmesg/,$d' ref-api.txt
| grep -v '^$') meecho-api.txt`.

| Что | panfrost | MEECHO |
|---|---|---|
| версия | 1.2.0 `panfrost` / `20180908` / `panfrost DRM` | то же |
| `GET_CAP` | SYNCOBJ 1, PRIME **3**, TIMESTAMP_MONOTONIC 1, SYNCOBJ_TIMELINE 0, прочее `ENOTSUP` | то же, но PRIME **0** — буферов-дескрипторов пока нет |
| параметры 0–40 | `GPU_ID` 0x7402/0x1000, … `THREAD_TLS_ALLOC` 0x400, `AFBC` 0; 41–44 `EINVAL` | то же, из тех же регистров |
| места буферов | 0x2000000, 0x2004000, 0x2200000, 0x2008000, куча 0x2600000, 5000 байт → 0x2005000, закрытый и новый → 0x2004000 | то же, те же номера дескрипторов |
| токен `MMAP_BO` | 0x100000000 | 0x10002000000 (метка; смысла не несёт) |
| ошибки | `EINVAL`/`ENOENT`/`EFAULT`/`ENODEV` на каждый неверный вызов; `MADVISE` берёт любой совет | то же |
| сроки | цепочка из 32768: `EBUSY` (срок прошёл), `ETIMEDOUT` (+1 мс), потом `ok` за 18.7 мс | то же, 20.0 мс |
| отказ задания | `WAIT_BO` ok, **ожидание объекта ok**, заголовок 0 — клиент не узнаёт ничего, кроме `dmesg` | `WAIT_BO` ok, **ожидание объекта `EIO`** — намеренно |
| два клиента | оба на 0x2000000, окна 0 и 1; отказ A — 0 у обоих ожиданий, A 199/0, B 200/0 | окна 1 и 2 (0 держит самопроверка); A — `EIO`, A 199/0, B 200/0 |

Замечено у panfrost: однажды, через ~0.5 с после отказа, его
планировщик поймал таймаут (`gpu sched timeout, js=1, status=0x8`) и
сбросил ускоритель; задание, попавшее на сброс, кончилось с заголовком 0
и `ok` на всех ожиданиях. Поэтому `jobprobe.py api` ждёт секунду перед
кучей.
