# Веха 8.2 на плате: что делать в первую сессию с железом

Драйвер `sdmmc` написан, собирается и проверен двумя хостовыми стендами
(111 проверок). Железом не проверен ничем. Ниже — порядок, в котором его
стоит трогать, и что означает каждый отказ.

## Прежде всего: убедиться, что консоль пишет

Цикл сам по себе работает и проверен: `board-deploy.ps1 -Boot` кладёт сборку
в `/boot` по ssh и взводит флаг, U-Boot снимает флаг и грузит MEECHO,
`/sbin/reboot` из MEECHO (или питание) возвращает Armbian вместе с ssh.
Вендорский `boot.scr` не тронут, его копия в `/root/boot.scr.vendor-backup`.

Чего не хватает — **наблюдения**. В первом прогоне COM3 пропал с
Windows-хоста ровно на загрузке MEECHO и не вернулся даже после возврата
Armbian; причина не установлена (объяснение «USB раздаётся с самой платы»
оказалось неверным — он воткнут в другую машину).

Поэтому порядок такой и он от причины не зависит:

1. Расшарить USB-TTL, дождаться COM3 на хосте.
2. **Проверить, что консоль действительно пишет**, пока плата на Armbian:
   `bash ~/bin/board-run.sh 'uname -sr'` — должен прийти ответ.
3. Открыть запись консоли и только потом взводить флаг.

Загрузка MEECHO без живой консоли ничего не сообщает, а стоит попытки.

## Состояние на плате после ночи 2026-09-07

- `/boot/fixup.scr` — положен. Вендорский `boot.scr` **не тронут**, его копия
  в `/root/boot.scr.vendor-backup`.
- `/boot/meecho/kernel.bin`, `/boot/meecho/boot.mba` — свежая сборка с
  `sdmmc`, `mkfs.mfs`, `dd` и `df` (`boot.mba` md5 `16f0cc5e…`).
- `/boot/meecho.go` — флага нет: U-Boot снял его сам на первом прогоне.
  Проверить: `board-deploy.ps1 -Status`.
- eMMC (`/dev/mmcblk1` в Linux, 61 079 552 сектора) — разделов нет,
  затирать разрешено. **На нём лежит образец, записанный из Armbian**, то
  есть заведомо исправным драйвером: в секторах 0, 1, 1234, 2047, 1000000,
  61079000 и 61079551 повторяется строка `MEECHO SECTOR <номер, 10 цифр>`.
  Это делает первое чтение из MEECHO сверкой с чужой записью, а не с самим
  собой.

## Порядок работ

### 0. Обновить сборку на плате и загрузиться в MEECHO

```powershell
D:\minix\port\board-deploy.ps1            # только скопировать
D:\minix\port\board-deploy.ps1 -Boot      # скопировать, взвести флаг, reboot
```

Корень при этом остаётся ramdisk в памяти (`bootramdisk=1`) — то есть
загрузка ровно та, которая на плате уже работала. Драйвер стартовать вручную:
так первый прогон нового кода не стоит на пути к приглашению `login`.

Ожидается: `login:`, вход `root` без пароля.

### 1. Поднять драйвер руками, с подробным журналом

```
/sbin/minix-service up /service/sdmmc -dev /dev/c0d0 -label sdmmc_0 \
	-args "instance=0 log_level=3"
```

Что должно напечататься:

```
sdmmc(info)mmc@fe310000: rockchip,dwcmshc-sdhci at 0xfe310000 (65536 bytes),
           irq 51, 8-bit bus, up to 200000000 Hz, soldered
sdmmc(info)SDHCI N.00 at 0xfe310000, base clock ... Hz, caps 0x...
sdmmc(debug)after init: state ... ctl ... pwr ... clk ... ...
sdmmc(debug)CID 700100504a333033320230161381cb00  CSD d02701320f5903ffffffffef8a400000
sdmmc(info)write cache on, 128 KiB
sdmmc(info)eMMC "PJ3032": 61079552 sectors (29824 MiB), 8-bit bus at ... Hz, high speed
```

**Строку CID/CSD сверить посимвольно** с тем, что печатает Linux в
`/sys/class/mmc_host/mmc1/mmc1:0001/{cid,csd}` — они выписаны выше и уже
совпали на стенде. Расхождение на байт означает, что сдвиг ответа R2 неверен,
и дальше идти нельзя.

Что означают отказы:

| Что напечатано | Где искать |
|---|---|
| `no SD/MMC controller this driver knows is in the device tree` | `fdt_fetch` не принёс дерево, или узел назван иначе. Сверить с `/proc/device-tree` |
| `cannot map registers at 0xfe310000; not granted by RS?` | Строка `devicetree "rockchip,dwcmshc-sdhci";` не доехала в `system.conf` образа |
| `reset 0x1 did not complete` | Контроллер держится в сбросе. Смотреть дамп регистров |
| `internal clock never settled` | Попробовать бит 1 регистра MISC_CON по смещению 0x81c (см. комментарий в `sdmmc_sdhci.c`) |
| `no card answered` | CMD1 не отвечает. Дамп регистров, `PRESENT_STATE` |
| `the card reports no capacity` | EXT_CSD прочитан не тот. Сверить CID/CSD |

### 2. Сырые сектора раньше файловой системы

**Сначала чтение того, что записал не он.** На eMMC уже лежит образец,
положенный из Armbian, и это самая ценная проверка во всём списке: она
сверяет драйвер с заведомо исправным, а не с самим собой.

```
dd if=/dev/c0d0 bs=512 count=1 skip=1234    | grep "SECTOR 0000001234"
dd if=/dev/c0d0 bs=512 count=1 skip=1000000 | grep "SECTOR 0001000000"
dd if=/dev/c0d0 bs=512 count=1 skip=61079551 | grep "SECTOR 0061079551"
```

Последняя строка — ещё и проверка края: это последний сектор устройства, и
попасть в него можно только если ёмкость посчитана верно и аргумент команды
не обрезан.

Многоблочное чтение (буфер драйвера — 32 КиБ, то есть 64 сектора; запрос
длиннее раскладывается на несколько команд, и склейка кусков — то место,
которое стенд проверяет, а железо может опровергнуть):

```
dd if=/dev/c0d0 of=/tmp/big bs=512 count=100 skip=0
ls -l /tmp/big
grep -c "SECTOR 0000000001" /tmp/big
```

**Потом запись.**

```
date > /tmp/mark
dd if=/tmp/mark of=/dev/c0d0 bs=512 count=1 seek=100
sync
dd if=/dev/c0d0 of=/tmp/back bs=512 count=1 skip=100
cat /tmp/back
```

И то же самое проверить **из Armbian** после возврата: записанное из MEECHO
должно читаться из Linux по тому же смещению. Разница между записанным и
прочитанным — это и есть класс ошибок, который QEMU не показывает.

### 3. Файловая система

Таблицу разделов **не делаем**: том занимает всё устройство, как это уже
сделано на диске в QEMU. Причина не только в простоте — пустой eMMC без
таблицы разделов U-Boot не считает загрузочным, и порядок загрузки не
меняется. Появится MBR — U-Boot может предпочесть eMMC карте.

```
/sbin/mkfs.mfs -4 /dev/c0d0
/bin/fsck_mfs -s /dev/c0d0
mount /dev/c0d0 /mnt
df
echo hello > /mnt/file
sync
umount /mnt
/bin/fsck_mfs /dev/c0d0
```

### 4. Корень с eMMC

```powershell
D:\minix\port\board-deploy.ps1 -Boot -RootEmmc
```

Это ставит `/boot/meecho/root_emmc`, и `fixup.scr` передаёт
`rootdevname=c0d0 blkdrv=sdmmc console=tty00` вместо `bootramdisk=1`.
Корень на eMMC требует, чтобы там уже был том из пункта 3 с `/etc/rc` и
прочим — то есть содержимое ramdisk надо туда сначала переписать. Как это
делает QEMU-сборка, видно в `ramimage.sh -d` (`proto.disk`, `rc.disk`).

**Критерий вехи:** записанное переживает `reboot` и `poweroff`, `fsck` на
чистом томе молчит, а на порченом — чинит.

### 5. Что осталось за вехой сознательно

- **DMA (IDMAC).** Обмен идёт через FIFO процессором. Причина и что нужно
  сделать раньше — `PORTING-LOG.md`, «Кэши и DMA». Коротко: сначала новый код
  `sys_vmctl` для обслуживания кэшей, потом DMA прямо в страницы
  пользователя через `sys_vumap()`.
- **Прерывание.** Все ожидания — опрос с предельным сроком. Линия 51 уже
  выдаётся RS, добавление ничего снаружи не меняет.
- **HS200/HS400.** Требуют обучения линии задержки. Карта идёт на HS52,
  восемь бит.
- **Драйвер SD-карты** (`mmc@fe2b0000`, dw-mshc). Второй файл рядом с
  `sdmmc_sdhci.c` и вторая строка в таблице `sdmmc_host.c`; слой карты не
  двигается.
