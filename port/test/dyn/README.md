# Динамическая линковка: тест, и один дефект, найденный им

## Тест

`dyn.c` — программа, которая доходит до `main()` через `ld.elf_so`. Собрать и
поставить в `DESTDIR`, откуда её возьмёт корень на диске:

```sh
bash port/test/dyn/build.sh
DISK_FRESH=1 bash ~/bin/ramimage.sh -d -r
# /usr/bin/dyntest
# LD_BIND_NOW=1 /usr/bin/dyntest
```

Гонять надо оба раза: `.rela.plt` обрабатывается двумя разными путями, и
до 2026-09-10 сломаны были оба, но по-разному. Разбор — `PORTING-LOG.md`,
«Динамическая линковка».

`build.sh` отказывается ставить двоичный файл без `PT_INTERP`: статически
слинкованный тест прошёл бы и не доказал ничего.

## `fpfork.c` — своя ли у процесса область под FP-регистры

**Дефект найден и починен 2026-09-10.** `minix/tests/test2` в динамической
сборке портил свои данные, в статической — нет; выглядело это как разовое
обнуление одного регистра SIMD (`v31`) между двумя оборотами векторного
цикла. К динамической линковке дефект отношения не имел: `do_fork()`
восстанавливал указатель `p_seg.fpu_state` из-под `#if defined(__i386__)`, и
на aarch64 ребёнок получал **область сохранения FP своего родителя**. Пока
ребёнок не сделает `exec` (тот через `arch_proc_init()` выдаёт слоту его
область назад), ленивое переключение FP раз за разом выдавало каждому из
двоих то, что оставил другой. Полный разбор — `PORTING-LOG.md`, «Один
регистр SIMD».

Зонд написан по разбору, а не по симптому, и **статический** — это и
отделяет дефект от загрузчика:

```sh
aarch64-elf64-minix-gcc -O2 -Wall -o fpfork fpfork.c
install -c -m 755 fpfork ~/dest-evbarm64/usr/bin/fpfork
DISK_FRESH=1 bash ~/bin/ramimage.sh -d -r
# /usr/bin/fpfork
```

Родитель трогает FP до `fork` (как `test2` — печатью из `start()`), потом
кладёт узор в `v16..v31` и крутит целочисленный цикл без единого вызова;
ребёнок крутит SIMD. Ответ — одна строка:

```
FP state is the process's own       область на процесс, всё в порядке
FP state shared with the child      общая область; рядом: v31 clobbered: 0x0 0x0
child never ran: this run proves nothing
```

Третий случай — не отказ, а отвод: за регистровый файл никто не боролся, и
прогон ничего не проверил. Зонд говорит это вслух, чтобы не пройти молча.

## `fpfault.c` — переживает ли состояние FP отказ страницы

Кладёт узор в `v16..v31`, берёт 64 отказа страницы подряд на нетронутых
страницах bss и читает регистры обратно. Собирать статически, `-O2`.

Ответ был и остаётся «переживает». К дефекту выше он отношения не имел и
иметь не мог: в нём один процесс, а там нужны два, спорящие за регистровый
файл. Оставлен как есть — вопрос, на который он отвечает, законный.

## Что из этого стоит запомнить

**Обход, который прячет симптом, не свидетельствует о причине.** Здесь их
было три — `LD_BIND_NOW=1`, `-fno-tree-vectorize` и «маленький повторитель
не портится», — и все три указывали в сторону от дефекта: первые два
меняют порядок событий и то, живёт ли счётчик цикла в регистре SIMD вообще,
третий не воспроизводил из-за неназванного условия.
